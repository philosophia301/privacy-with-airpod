# Agent workflow — 제품 작업과 함께 실험함

목적은 같은 작업의 품질을 유지하면서 시간과 토큰 소모를 최소화하는 모델·orchestration 방안을 찾는 것임. 참고 프로젝트의 성공 수치를 이 프로젝트의 성과로 사용하지 않음. 제품 착수·승인·리뷰 절차는 [작업 규칙](../rules/workflow.md)이 소유함.

## 구분할 개념

| 개념 | 이 프로젝트에서의 뜻 |
| --- | --- |
| Subagent | 메인이 좁은 책임을 맡기는 별도 agent 세션 |
| Orchestration | 작업·의존성·위임·질문·종료·회수를 추적하는 조정 방식 |
| Static workflow | 시작 전에 역할·순서·조건 분기를 정한 진행 방식 |
| Dynamic workflow | 관측한 불확실성과 결과에 따라 메인이 다음 역할·범위를 선택하는 방식 |

서로 대체하는 네 도구가 아님. subagent를 orchestration으로 관리하면서 static 또는 dynamic 방식을 쓸 수 있음. Dynamic은 제품 scope·권한·완료 조건을 임의로 바꾸는 권한이 아님.

## 이번 프로젝트의 초기 운영

메인이 문서 작성·제품 결정 정리·통합 보정을 소유하고, 별도 조사자는 좁은 자료 조사, reviewer는 한 관점의 검토를 맡음. 구현자·tester 추가는 실제 구현 과제에서 필요성을 판단함. 같은 파일을 동시에 수정하지 않음.

Orca orchestration을 사용할 때는 실제 Run·Task·Dispatch와 종료 보고를 확인함. Run은 작업 묶음, Task는 과제, Dispatch는 한 agent에 맡긴 실행 시도임. 현재 CLI의 안내를 읽고 지원하는 명령만 사용하며 세션 ID를 추측하거나 내장 subagent 실행을 Orca 실행으로 기록하지 않음.

실행 중인 worker가 있으면 유효한 완료·실패·질문을 회수하고 모든 결과를 처리함. 완료된 worker는 후속 Task에 바로 재사용하거나 runtime의 release 절차로 정리함. timeout만으로 완료나 실패를 단정하지 않음. 제품 작업과 관련 없는 사용자 터미널은 건드리지 않음.

## 위임 계약

각 과제에 목적, 입력 판본·파일, 읽기/쓰기 소유권, 금지 범위, 완료 증거, 실행할 검사, 예산, 중단·보고 조건을 전달함. 예산은 파일 수·후보 수·보정 횟수처럼 셀 수 있는 단위로 적으며 runner가 강제하지 않으면 강제 한도라고 부르지 않음.

전제가 실제 파일과 다르면 추측해 구현하지 않고 차이를 보고함. 재사용할 정본·타입이 아직 준비되지 않았으면 임시 복사본을 만들지 않고 필요한 부분만 기다림.

보고는 한국어로 판정·근거·미확인·실행 결과를 남김. 저장소 내부 근거는 상대경로와 줄 번호, 외부 자료는 원본 위치와 열람 방법을 사용함. `file:line`이나 실제 관측이 없으면 확인된 결함과 구분함.

메인은 보고를 그대로 채택하지 않음. 지적의 계약 위반 여부와 현재 파일을 대조하고 중요한 실행 경계를 검증함. 같은 판본의 유효한 검사까지 무조건 중복 실행하지 않되 대역의 통과를 실물 완료로 바꾸지 않음.

## 비교할 초기 실험

| 실험 | 구성·변경 축 | 판정 |
| --- | --- | --- |
| E001 초기 문서 작업 | 메인 작성 + 읽기 전용 reference 조사. 필요 시 결정 누락 리뷰를 추가 | 역할 분담의 실제 실행 여부·채택/기각·보정 기록. 대조군 없는 운영 관측 |
| E002 static 기준선 | 다음 실제 spec 또는 기술 과제의 고정 판본에 조사→작성→독립 검토 순서를 사전 고정 | 근거 누락·오탐·확인된 결함·메인 보정·전체 시간 |
| E003 dynamic 비교 | 같은 읽기 전용 과제 판본에서 메인이 불확실성에 따라 조사/검토 선택. E002와 완료 조건·모델 조건 유지 | 선택한 역할과 이유, 같은 품질 기준, 운영 포함 비용 |

E002/E003은 계획이며 실행 결과가 아님. 순차 비교의 학습 효과를 줄이도록 각 후보는 fresh 문맥에서 수행하고 앞선 답을 넘기지 않음. 후보 순서·캐시·서버 지연을 기록함. 파일을 동시 편집하는 A/B 대신 읽기 전용 후보 결과를 비교함.

양쪽 후보에 동일한 독립 최종 검토를 적용함. dynamic에서도 완료 검증을 생략하지 않음. 위임 자체의 이득까지 비교하려면 별도 메인 단독 기준군이 필요하며 이 두 후보만으로 그 이득을 주장하지 않음.

한 번에 모델·effort·역할 수·workflow를 모두 바꾸지 않음. 시간 측정 시 경쟁 작업의 유무를 남기며, 실제 품질·토큰·비용을 볼 수 없으면 미관측으로 표시함. 실험을 위해 제품 동작·승인 조건·검증 gate를 낮추지 않음.

## 기록과 중단

실험 기록은 날짜·질문·입력 판본·역할·실제 runtime 식별자·실행 범위·추가 발견·메인 보정·미실행·재검 조건을 포함함. 토큰·비용·시간은 관측 가능한 원본에서만 산출하고 누락 값을 추정 숫자로 채우지 않음. 준비·회수·검증·보정도 전체 비용에 포함함.

소유권 침범·범위 초과는 즉시 중단·보고 대상임. 동일한 필수 누락이 한 번의 보정 뒤에도 남으면 재위임을 자동 반복하지 않고 메인이 소유권과 원인을 재판정함. 제품 작업을 끝내는 데 필요 없는 비교는 뒤로 미룸.

현재 실험 기록은 [E001](experiments/2026-09-14-bootstrap.md)과 [첫 구현 관측](experiments/2026-09-14-implementation.md)에 있음. 참고 근거는 [references](../references.md)가 소유함.

## 모델·시간·토큰 최적화 — 2026-09-14 사용자 지시

현재 실행 중인 구현·리뷰는 마무리함. 이후에는 Astra를 모든 worker의 기본값으로 상속하지 않음. 좁은 탐색·정형 수정은 사용 가능한 낮은 비용의 모델부터 선택하고, 계약 누락이나 실패 근거가 있을 때만 상향함. 모델 이름만으로 적합성을 확정하지 않으며 실제 runtime에서 선택한 모델·effort를 기록함.

위임 전에 메인 단독 처리와 비교함. 짧은 단일 작업은 직접 수행하고, 독립 작업이 충분히 크거나 별도 검토가 필요한 경우에만 worker를 사용함. 전달 문맥은 필요한 파일·계약·검사로 제한하고 중복 조사·빈번한 상태 조회·유휴 worker를 줄임. Static은 반복 가능한 좁은 작업, dynamic은 확인된 불확실성에 따른 추가 조사·상향에 사용함.

비교에는 준비·전달·대기·통합·리뷰·재작업을 포함한 전체 소요 시간과 관측 가능한 입력/출력 토큰을 사용함. 비용은 실제 모델 가격과 사용량을 확인할 수 있을 때만 산출함. 한 번에 모델 또는 workflow 한 축을 바꾸고 동일 품질 기준으로 비교함. 미관측 비용을 절감 성과로 주장하지 않으며 최적화 자체가 제품 작업보다 비싸지면 추가 비교를 보류함.

## 근본 원인 조사와 Luna 운영 — 2026-09-14 최신 사용자 지시

Luna subagent를 동시에 최대 20개까지 사용할 수 있으며 독립 조사·구현·검토에 적극 활용함. fast mode는 금지함. 실행 시 모델과 fast mode 비활성 여부를 지원하는 runtime 설정/receipt로 확인하며, 확인하지 못한 항목은 준수 확인으로 기록하지 않음. 20개는 동시 사용 상한이며 같은 조사 반복이나 빈 과제를 만들기 위한 목표 수가 아님.

화면 전환 후속은 OS 창 이동, 캡처 프레임 시각, native/GPU 중복 합성, 독립 재현·회귀 관점으로 소유권을 나눔. 메인은 독립 보고를 같은 판본·시간축과 대조해 원인과 추정을 구별함. 사용자 피드백을 자동 검사 성공으로 덮지 않고 원인 분리 실험 후 수정을 결정함. 기존 시간·토큰 최적화, 작은 문맥 전달, 완료 worker 회수·release 원칙은 유지함.
