# 작업 수행 절차

ROADMAP의 한 단위를 TODO의 작은 Phase로 나누고 결정·검증·리뷰 경계를 유지함. 이 문서는 제품 작업 절차이며 agent를 몇 개 쓰는지는 [agent-workflow](../agent-workflow/README.md)가 정함.

## 문서마다 한 가지 정본을 둠

문서 소유권과 경로는 [AGENTS 배치 지도](../../AGENTS.md#배치-지도)가 정함. TODO는 현재 진행을 위한 문서이며 코드·안정 계약이 TODO의 문장에 의존하게 하지 않음. 승인 기록과 측정 수치를 여러 문서에 복사하지 않음.

## Phase 흐름

```text
목적·범위·착수 조건 확인 → 구현 또는 조사 → 필요한 검증 → 미커밋 리뷰 → 승인 범위에 따른 다음 작업
```

Phase마다 목적·관측 가능한 완료 조건·검증·열린 결정을 먼저 적음. 순수 판단, 센서 연결, 화면, 권한처럼 바뀌는 경계를 기준으로 [검증 수준](testing-levels.md)을 선택함.

승인된 가역적 작업은 중간 허락을 반복 요청하지 않음. 기존 경로를 우선 확장하며 새 구조·의존성이 필요하면 부족한 보장과 영향을 설명함.

검증의 종료 코드와 요약을 확인함. 실패는 같은 Phase에서 원인을 좁혀 고치며, 해결하지 못한 항목은 남은 위험과 미완료 조건으로 공개함. 실행하지 못한 검증을 통과로 쓰거나 gate를 낮춰 닫지 않음.

## 예상 밖 finding

Finding은 작업 중 발견한 전제 오류·결함·추가 기회를 뜻함.

| 종류 | 대응 |
| --- | --- |
| 승인 범위 안의 결함·작은 중복 | 같은 Phase에서 수정·검증 |
| 제품 행동·권한·구조·완료 조건을 바꾸는 발견 | 영향받는 작업만 멈추고 근거·추천·대안을 사용자에게 제시 |
| 현재 범위 밖 개선 | TODO의 후속 후보로 기록하고 현재 작업은 진행 |
| 환경·도구 때문에 검증 불가 | 실패 원인·실행 범위·남은 관측을 공개하고 독립 작업은 진행 |

같은 Phase를 임의로 축소해 완료로 만들지 않음. 모든 작업을 중단하거나 별도 시스템을 만드는 것이 기본 대응은 아님.

## 리뷰와 반영

검증 후 변경을 미커밋 상태로 제시함. 무엇이 달라졌고 왜 필요한지, 실제 검증, 미검증과 위험, 사용자 결정이 필요한 지점을 함께 보고함. 리뷰 지적은 근거와 현재 판본을 대조한 뒤 반영함.

커밋은 사용자가 명시적으로 요청·승인한 범위에서만 함. 모호한 ‘좋아’를 커밋·push·PR 승인으로 넓히지 않음. push·PR·릴리스·외부 반영은 각각 승인 범위 확인이 필요함. 커밋 메시지는 파일 목록보다 판단 이유를 설명함.

Phase 종료 시 TODO에 목적·검증·남은 위험을 짧게 남김. 장기 기술 결론은 소유 문서로 옮기고 단위 전체 완료는 ROADMAP에 반영함. 기준을 바꿨다면 과거 실패를 새 기준의 성공으로 덮어쓰지 않음.
