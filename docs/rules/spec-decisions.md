# Spec을 함께 결정하는 방법

사용자가 결과를 판단할 수 있는 행동을 먼저 정하고, 구현 방법과 사실 조사를 분리함. 중요한 결정을 숨기지 않되 뒤 기능의 모든 결정을 첫 실험의 선결조건으로 만들지 않음.

## 누가 무엇을 정하는가

| 대상 | 처리 | 이 앱의 예 |
| --- | --- | --- |
| 제품 행동·UX·권한·수집·저장 계약·지원 범위·외부 계약의 새 정책 | 추천·대안·영향을 제시하고 사전 결정받음 | 연결이 끊기면 가릴지, 자동 해제할지, 카메라를 쓸지 |
| 승인된 행동·경계와 명시적 위임 안의 내부 방법 | 구현자가 선택하고 중요한 이유를 리뷰에 남김 | 앱 구조·감지 알고리즘·렌더링·빌드 방법 |
| 문서·코드·실행으로 확인할 사실 | 조사하고 관측 경계를 밝힘 | 대상 AirPods에서 motion sample이 도착하는지 |
| 현재 단위에 필요 없는 정책 | 결정 주체·시점·이번 제외 범위를 남김 | App Store 배포·자동 업데이트 |

가역적이라는 이유로 새 UX·권한을 자율 확정하지 않음. 사용자 침묵·문서 작성 요청·하위 agent 제안은 제품 승인 아님. 다른 프로젝트의 승인 이력도 이전하지 않음.

2026-09-14 사용자 지시로 구현 방법의 자율 위임이 적용됨. 위임 정본은 [spec](../spec.md#구현자에게-맡긴-범위--사용자-위임)임. 구조·의존성 선택이 위임 경계 안이면 이유를 남기고 진행하며, 새 권한·서비스·보관 계약·사용자 행동으로 이어지면 영향받는 정책만 먼저 결정함.

## 질문은 결정의 끝이 보이게 함

질문 전에 이번 흐름, 필수 결정, 구현자 위임, 보류 범위를 보여줌. 연결된 선택은 한 흐름으로 제안하고 이견이 있는 항목부터 정함. 하나의 승인 뒤에 숨겨 둔 필수 질문을 계속 추가하지 않음.

추천에는 이유·허용할 손실·대안이 더 나은 조건을 붙임. 감지 누락과 작업 방해처럼 충돌하는 결과를 함께 밝힘. 기술 조사로 답할 수 있는 문제를 사용자 취향 질문으로 넘기지 않음.

## Spec은 사용자 행동의 정본임

spec에는 조건·성립 범위·보이는 결과를 씀. 예를 들어 ‘AirPods를 다시 연결하면 화면이 즉시 보인다’는 제품 결정이며 callback 구현 방법은 기술 설계임.

각 결정은 상태, 출처, 선택, 이유, 허용한 결과를 남김. 사용자 요청·승인·가정·제안을 구분하고 날짜를 붙임. 이미 구현했거나 테스트가 통과했다는 사실은 제품 선택의 정당화가 아님.

저장·복구를 추가하기 전에 ‘없으면 무엇이 안 되는가’와 ‘그 행동이 필요한가’를 확인함. 화면 내용·원시 센서·사용 이력을 당연히 저장하지 않으며 수집·보관·삭제 계약은 사람이 정함.

## 착수 조건과 재논의

이번 단위에 필요한 네 조건을 닫은 뒤 승인 범위 안에서 진행함.

1. 제공할 행동과 이번에 하지 않을 것.
2. 실패 시 결과와 허용할 누락·오탐·지연.
3. 권한·저장·구조·의존성 경계와 내부 위임 범위.
4. 완료를 판정할 관측과 검사.

새 근거가 승인된 행동과 충돌하면 [finding 절차](workflow.md#예상-밖-finding)를 따름. 단순 개선 가능성 때문에 결정을 다시 열지 않으며, 확인되지 않은 기술 가정은 성공·불가능 어느 쪽으로도 임의 확정하지 않음.

승인된 선택은 spec, 현재 미결·다음 행동은 TODO, 기술 증거는 조사·실험 문서가 소유함. 이 문서는 결정 가이드이며 자동 승인 Hook이 아님. 출처는 [reference](../references.md)에 있음.
